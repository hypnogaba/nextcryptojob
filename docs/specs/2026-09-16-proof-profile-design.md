# Профіль-доказ на сторінці картки (2026-09-16)

## Навіщо
Людина отримала бал, але на кожну вакансію все одно подає CV. Профіль-доказ замінює CV там,
де це можливо: сторінка й PDF, які ми збираємо самі з того, що вже є. Це **доказ навичок, а не
повне CV**: історії роботи немає, завантаження старого CV немає, анкета не змінюється.

Обмеження власника: база людей не має стати безкоштовно доступною (її купують компанії в CRM).
Тому публічний вигляд анонімний, повний вигляд лише за особистим ключем людини або в PDF.

## Що не робимо
Супровідний лист, історія роботи, завантаження CV, редагування тексту фактів, кілька ключів для
різних компаній, лічильник переглядів, нові запити до джерел (назви репозиторіїв, мови).

## 1. Сторінка `/c/<код>`: два вигляди
Та сама сторінка картки. Картка, розбір балу й дії власника лишаються як є; під ними новий блок
**Proof**.

| Блок | Без ключа | З ключем `?k=` | PDF |
|---|---|---|---|
| Картка, бал, розбір балу | так | так | так |
| Ролі, формат роботи | так (місто не називається) | так, з містом | так, з містом |
| Proof: факти з `source_facts` | так, без імен і посилань | так, з іменами й посиланнями | так |
| Слова людини (`role_text`, `target_text`) | ні | так | так |
| Посилання, додані людиною | ні | так | так |
| Адреси гаманців | ні | лише якщо `show_wallet = 1` | так само |
| Контакт (Telegram-нік, пошта) | ні | так | так |

Слова людини без ключа сховані: у вільному тексті бувають ім'я, компанія, місто.

**Факти Proof** беруться лише з полів `docs/contracts.md` §3, по одному рядку на факт:
- GitHub: `mergedPrsElsewhere`, `commits12m`, `reviews12m`, `stars`, `followers`, рік `createdAt`,
  `reposPushed12m`, `reposWithSite`. З ключем: посилання на профіль GitHub з `identities`.
- X: `followers`, `kol`, `own30d`, `ownAvgViews`. З ключем: посилання на профіль X.
- Гаманці: вік (найраніший `firstTs`), кількість транзакцій, мережі з активністю, угоди, обсяг
  Hyperliquid. Адреси лише за правилом з таблиці.
- YouTube: `subscribers` (якщо не сховані), `avgViewsRecent`, `videos90d`. З ключем: посилання.
- Сайт: `feedItems`, `items90d`, дата `latestTs`. З ключем: адреса.
- Аудити: `earningsUsd`, `high`, `contests`. З ключем: профіль Sherlock.

Поле `null` не друкується (ніколи не «0»). Джерело з `facts_json = NULL` не має рядків.
Числа друкуються коротко (`1.2k`), роки цілими.

**Дані.** Нова функція `profileView(card, facts, prefs, full: boolean)` у `web/src/lib/card/profile.ts`
віддає один об'єкт; його беруть і сторінка, і PDF. Функція чиста (без D1), читання в
`card-data.ts` поруч з `loadCardView`, одним `cache()` на запит. Анонімний вигляд будується з
того самого об'єкта відкиданням полів, а не окремим кодом, щоб поля не просочились випадково:
тип анонімного вигляду не має полів `url`, `handle`, `words`, `contact`, `links`, `address`.

**Ключ.** Перші 32 hex-символи `HMAC-SHA256(SESSION_SECRET, "profile-key:<user_id>:<key_version>")`.
Сам ключ ніде не зберігається, у базі лише номер версії: сервер виводить очікуваний ключ для
власника картки й порівнює за сталий час. Reset збільшує версію.
Неправильний або старий ключ дає анонімний вигляд без помилки й без підказки.
Відповідь з ключем: `robots noindex`, `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`.
Канонічна адреса й og-теги лишаються без ключа.

## 2. Керування в `/profile`
Новий блок **Your proof profile** під карткою. З'являється сам, коли в людини є картка.

1. Попередній вигляд повного профілю і посилання **See public view** (анонімний вигляд).
2. **Copy apply link**: `/c/<код>?k=<ключ>`. Ключ з'являється при першому натисканні
   (версія 1) і показується лише власнику.
3. **Hide / show** біля кожного факту і біля слів людини. Схований пункт зникає скрізь (сторінка,
   ключ, PDF). **Бал і розбір балу не змінюються**: слабке джерело не сховати.
4. **Add link**: до 5 посилань, назва до 40 символів + адреса лише `https://`, перевірка тим самим
   кодом, що й поле сайту. Показ лише з ключем і в PDF, з позначкою `added by owner`, на бал не
   впливають.
5. **Show wallet addresses**: перемикач, типово вимкнений.
6. **Reset apply link**: новий ключ, старе посилання одразу дає анонімний вигляд. Коротке
   пояснення поруч, без діалогу.
7. **Download PDF**.

**Таблиця** (одна міграція `0026_profile_prefs.sql`):
```sql
CREATE TABLE IF NOT EXISTS profile_prefs (
    user_id      TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
    key_version  INTEGER NOT NULL DEFAULT 0,   -- 0 = ключа ще немає; reset = +1
    hidden_json  TEXT NOT NULL DEFAULT '[]',   -- ["github.stars", "words.role", …]
    links_json   TEXT NOT NULL DEFAULT '[]',   -- [{"label":"…","url":"https://…"}], до 5
    show_wallet  INTEGER NOT NULL DEFAULT 0,
    updated_at   TEXT NOT NULL DEFAULT (datetime('now'))
);
```
Немає рядка = типові значення. Кожна зміна пише подію в `audit_log` (без ключа й без адрес).

## 3. PDF
Маршрут `GET /c/<код>/profile.pdf`. Доступ: правильний `?k=` або сесія власника картки;
інакше 404. Бібліотека `pdf-lib` + `@pdf-lib/fontkit`, шрифт Inter (звичайний і жирний),
QR-код з `qrcode-generator` (уже в проєкті).

A4, одна сторінка, якщо влазить, інакше дві:
1. Шапка: ім'я для показу, ролі, remote/місто, контакт, посилання з ключем + QR.
2. Бал і рівень, розбір балу списком (джерело, вага, бали).
3. Proof з клікабельними посиланнями.
4. Слова людини.
5. Посилання людини з позначкою `added by owner`.
6. Низ: `Score formula <версія>, issued <дата>. Verify: <посилання з ключем>`.

Без зображення картки. Файл не зберігаємо: робимо на кожен запит, тож схований пункт і новий
ключ діють одразу. Назва файлу `nextcryptojob-<код>.pdf` (без імені людини).
Відповідь: `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`.

**Перший крок реалізації:** виміряти стиснутий розмір Worker до і після `pdf-lib` + шрифту проти
ліміту 10 МБ. Якщо не влазить, PDF іде в окремий Worker з доступом лише до читання D1.

## 4. Помилки й безпека
- Картки немає або вона перенаправлена: як зараз (redirect або 404), ключ не переноситься.
- Бал змінився після видачі: Proof показує поточні факти, розбір балу поводиться як зараз
  (`backMissing`).
- Джерело без фактів: рядків немає, причину прогалини в Proof не показуємо (вона вже є в розборі).
- Ключ ніколи не пишеться в наші логи, `audit_log`, `funnel_days` чи аналітику: код
  логує шлях без параметрів запиту.
- Лідерборд і og-картинки завжди ведуть на адресу без ключа.
- Власник, що видалив акаунт: `ON DELETE CASCADE` прибирає налаштування, ключ перестає діяти.
- Дії в `/profile` (hide, links, reset) лише для власника, перевірка на сервері.
- Посилання людини: `rel="nofollow ugc noopener"`, `target="_blank"`.
- Юридичні тексти (`docs/legal/privacy-policy.md`, `how-scoring-works.md`): дописати, що повний
  профіль бачить лише той, кому людина дала посилання або PDF.

## 5. Тести
- `profileView`: анонімний вигляд не містить жодного url, handle, адреси, пошти, ніка чи слів
  людини (перевірка серіалізованого JSON на збіги з тестовими значеннями).
- `null` не друкується як 0; джерело без фактів не дає рядків.
- Схований пункт відсутній у всіх трьох виглядах; бал і розбір однакові зі схованими пунктами й без.
- Ключ: правильний дає повний вигляд, старий після reset, випадковий і ключ іншої картки дають
  анонімний.
- PDF: 404 без ключа і без сесії власника; з ключем відповідь `application/pdf`, текст містить
  бал і посилання; анонімних даних без ключа отримати не можна.
- Сторінка з ключем має `noindex`, `no-referrer`, `no-store`.
- Посилання людини: лише `https://`, не більше 5, назва до 40 символів.
- `next build` перед деплоєм (клієнтські компоненти не тягнуть серверний код).
